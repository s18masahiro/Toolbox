# brew-release-notes

Homebrew 週次チェック（launchd版 / ショートカット版）が出力した `brew-check-YYYY-MM-DD.md` を読み、
更新可能なパッケージごとにリリースノートを調べて `release-notes-YYYY-MM-DD.md` を同じフォルダに書き出す。

このスキルには2つの使い方がある。

- **A. 実行**：レポートを処理してまとめを書き出す（スケジュール済みタスクからの定期実行、または手動依頼）
- **B. スケジュール済みタスクの作成**：A を毎週自動で動かすタスクを登録する

どちらも最初に「0. レポートフォルダの確認」を行う。

## 守ること

- **`brew upgrade` などパッケージを変更する操作は絶対に実行しない。** 更新は利用者が手動で行う方針。
- 既存のレポート・ログは読むだけで変更しない。書き込むのは `release-notes-*.md` だけ。
- リリースノートに書かれていないことを推測で書かない。見つからなければ「見つからず」と書く。
- レポートの場所はパスを決め打ちしない。必ず「Cowork セッションまたはプロジェクトに紐づけられたフォルダ」から探す。

## 0. レポートフォルダの確認（A・B 共通）

1. `get_device_info` の `connectedFolders` で、この Cowork セッションまたはプロジェクトに紐づけられているフォルダを確認する。
   - device_bash では `$HOME/mnt/` 配下にマウントされている（`ls $HOME/mnt/` で名前を確認）。
2. 紐づけられたフォルダの中から `brew-check-*.md` を探す（例：`find $HOME/mnt/* -maxdepth 5 -name 'brew-check-*.md'`）。
   - 見つかったファイルが入っているフォルダを「レポートフォルダ」とする。
   - 複数のフォルダで見つかった場合は、最も新しいレポートがあるフォルダを使い、その判断を報告に書く。
3. 次のどれかに当たる場合は **紐づけなし** として扱う。
   - Mac につながっていない（remote-devices のツールが使えない、またはデバイスに接続できない）
   - `connectedFolders` が空
   - 紐づけられたフォルダのどこにも `brew-check-*.md` がない

**紐づけなしのとき**：その先の処理（A の実行・B のタスク作成）は行わずに中止し、ユーザーに次のように依頼する。

> レポートが入っているフォルダ（例：launchd版なら配置したフォルダ内の `reports/`、ショートカット版なら `~/brew-check`）が、
> このセッションにもプロジェクトにも紐づけられていないため、処理を中止しました。
> 次のどちらかでフォルダを紐づけてから、もう一度依頼してください。
> - Cowork セッションにフォルダを追加する（デスクトップアプリの「フォルダを追加」）
> - プロジェクトにフォルダを紐づける

`device_request_folder_access` でフォルダを勝手に追加しない。紐づけはユーザーに行ってもらう。

## A. 実行

### A-1. レポートを特定する

- レポートフォルダ内で最も新しい `brew-check-YYYY-MM-DD.md` を読む。
- 最新レポートが **8日以上前** なら「今週のレポートが生成されていない（週次チェックが止まっている可能性）」と報告して終了。
- 同じ日付の `release-notes-YYYY-MM-DD.md` が既にあれば、処理済みとして終了。

### A-2. 更新対象を抜き出す

- 「## 更新可能な formula」「## 更新可能な cask」のコードブロックを読む。
  - formula の行：`name (現在のバージョン) < 最新バージョン`
  - cask の行：`name (現在のバージョン) != 最新バージョン`
- どちらも「なし」なら、**ファイルは作らず**「更新なし」と報告して終了（doctor の警告件数があれば一言添える）。

### A-3. パッケージごとにリリースノートを調べる

各パッケージについて、現在のバージョン → 最新バージョンの間の変更を調べる。

1. 公式情報の場所を特定する（cloud の Bash で取得してよい）
   - formula：`https://formulae.brew.sh/api/formula/<name>.json` の `homepage` / `urls.stable.url`
   - cask：`https://formulae.brew.sh/api/cask/<token>.json` の `homepage` / `url`
2. GitHub でホストされていれば `gh` で取得する
   - `gh api repos/<owner>/<repo>/releases --paginate -q '.[] | {tag_name, published_at, body}'`
   - 現在〜最新の間のリリースをすべて対象にする（間のバージョンも飛ばさない）
   - Releases が空ならリポジトリの `CHANGELOG.md` / `NEWS` を確認
3. GitHub 以外なら WebSearch / web-fetch で公式のリリースノート・変更履歴ページを探す
4. 次の観点で拾う
   - **セキュリティ修正**：CVE 番号、"security", "vulnerability" などの記載
   - **破壊的変更・要注意**：設定や互換性の変更、非推奨・削除、メジャーバージョンアップ、移行手順
   - **主な変更**：新機能・不具合修正の要点（3〜5点程度）
5. 分類
   - 🔴 セキュリティ修正あり
   - 🟡 破壊的変更・要注意あり（セキュリティなし）
   - 🟢 通常の更新
   - ⚪ リリースノートが見つからない

更新対象が 15 件を超える場合は、🔴🟡 を優先して詳しく調べ、🟢 は1〜2行の要約にとどめる。

### A-4. ファイルを書き出す

レポートフォルダに `release-notes-<レポートの日付>.md` を device_bash で書き出す
（python などでファイルに書く。既存ファイルは上書きしない）。

```markdown
# Homebrew 更新内容まとめ — YYYY-MM-DD

元レポート: brew-check-YYYY-MM-DD.md

## サマリー
| パッケージ | 種別 | 現在 → 最新 | 分類 | 一言 |
|---|---|---|---|---|

- セキュリティ修正: n 件 / 要注意: n 件 / 通常: n 件

## 🔴 セキュリティ修正（先に確認）
（該当パッケージと CVE・影響の要点。なければ「なし」）

## パッケージ別の詳細
### <name>（formula|cask）現在 → 最新
- 分類:
- セキュリティ:
- 破壊的変更・注意点:
- 主な変更:
- 更新の目安: すぐ更新を推奨 / 内容を確認してから / 急がなくてよい
- 出典: <URL>

## brew doctor
（警告があれば要点を1〜3行。詳細は元レポート参照）

## 更新コマンド
個別に更新する場合:
    brew upgrade <name>
```

「更新の目安」はあくまで参考。セキュリティ修正があるものは「すぐ更新を推奨」、
破壊的変更があるものは「内容を確認してから」を基本にする。

### A-5. 報告

2〜3行で返す：更新件数、セキュリティ修正の有無（あればパッケージ名）、出力したファイルの場所。
詳細はファイルに書き、メッセージには書かない。無人実行では質問せず、判断した前提はファイルに明記して進める。

## B. スケジュール済みタスクの作成

1. **「0. レポートフォルダの確認」を必ず先に行う。** 紐づけなしなら、タスクは作成せずに中止し、上記の依頼文でユーザーに紐づけをお願いする。
2. 紐づけが確認できたら、scheduled task のツール（create_trigger）で登録する。
   - 名前：Homebrew 更新内容まとめ
   - 実行：毎週月曜 10:00（`CRON_TZ=Asia/Tokyo 0 10 * * 1`）※週次チェック（月曜 9:00）の後。ユーザー指定の時刻なので分をずらさない
   - `requires_local_device: true`（Mac のフォルダを読むため）
   - `folders`：レポートフォルダを含む、紐づけ済みのフォルダ
   - プロンプト（各回は新しいセッションで動くので、単体で通じる内容にする）：

```
brew-release-notes スキルの「A. 実行」に従って、Homebrew 週次チェックのレポートを処理してください。

- レポートは、この Cowork セッションまたはプロジェクトに紐づけられたフォルダから brew-check-*.md を探してください。
  紐づけられたフォルダがない、またはレポートが見つからない場合は処理を中止し、フォルダの紐づけをお願いする旨だけ報告してください。
- 更新可能なパッケージがあれば、各パッケージのリリースノートを調べ、セキュリティ修正・破壊的変更・主な変更をまとめた
  release-notes-YYYY-MM-DD.md をレポートと同じフォルダに書き出してください。更新がなければファイルは作らず「更新なし」と報告してください。
- brew upgrade などパッケージを変更する操作は絶対に行わないでください。
- 無人実行です。質問はせず、最後に2〜3行で結果（更新件数、セキュリティ修正の有無とパッケージ名、出力ファイル）を報告してください。
```

3. 登録後、実行時刻・紐づけたフォルダ・承認の設定（自動承認か、毎回確認か）をユーザーに1〜2文で伝える。
